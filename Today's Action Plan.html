이 프로젝트를 통해 무엇을 만들었고 무엇을 배웠는지 정리한다. 솔직하고 구체적일수록 신뢰도가 올라간다.
잘된 것: 의도한 대로 구현된 것, 특히 인터랙션과 연결해서 구체적으로 쓴다.
잘못된 것: 의도와 다르게 된 것, 아쉬운 것을 솔직하게 쓴다.
도전한 것: 처음 해본 기술이나 방식을 쓴다.
다음에 개선할 것: 구체적인 개선 방향을 쓴다. 테스트에서 발견했지만 이번에 고치지 못한 것이 있다면 여기에 쓴다.

10. 마무리 페이지: 가설 검증

2번 기획 의도에서 열었던 이야기를 사용자 기준으로 닫는 페이지다. 새로운 정보를 추가하는 페이지가 아니라, 앞에서 보여준 근거를 모아 결론을 내리는 페이지다.

꼭 체크할 것

처음과 끝을 연결하는 서사 2번 배경에서 시작된 이야기를 사용자 경험 기준으로 마무리한다.
검증 근거 03에서 세운 THEN이 실제로 일어났는지, 07의 테스트 결과(짝꿍이 실제로 보인 반응, 통과한 케이스)를 근거로 한 줄 쓴다.
짧고 인상적으로 길게 쓰지 않는다. 이 프로젝트가 만든 경험의 변화를 2~3문장으로 압축한다.
마무리 한 문장 케이스 스터디 전체를 관통하는 메시지를 한 문장으로 끝낸다.

너는 UI/UX 포트폴리오 케이스 스터디를 정리해주는 어시스턴트야. 첨부한 [가이드 파일]의 10페이지 구성에 맞춰, 내가 개인 작업한 프로젝트의 케이스 스터디 초안을 작성해줘. 프로젝트에 대한 내용은 전부 첨부한 내 작업 문서에서만 가져와. ## 첨부 파일 - case-study-interaction-guide.md : 케이스 스터디 작성 가이드 (페이지별 체크 항목) - 기획 문서: PROJECT_CONTEXT.md 정리한 기획 - design.md : 디자인 기준 문서 - prd.md : 요구사항 정의서 - testcases.md : 테스트 케이스 문서, 테스트 결과·수정 기록 - (있으면) 사이트 코드, 배포 주소, Figma 와이어프레임 링크 ## 먼저 할 일 작성에 들어가기 전에 첨부 문서를 모두 읽고, 아래 항목을 문서에서 찾아 한 줄씩 정리해서 보여줘. 문서에서 찾지 못한 항목은 "문서에 없음"이라고 표시해. 프로젝트명 / 한 줄 설명 / 타깃 사용자 / 사이트 구성(페이지) / 핵심 인터랙션 / 사용한 도구 / 요구사항 / 테스트 케이스 / 테스트 결과 / 수정 내용 ## 작성 규칙 1. 가이드의 10페이지 순서와 제목을 그대로 따른다. 각 페이지의 "꼭 체크할 것" 항목을 빠짐없이 채운다. 2. 첨부 문서에 있는 내용만 근거로 쓴다. 문서에서 확인되지 않는 것(기간, 배포 링크, 테스트 결과, 수정 내용, 수치 등)은 지어내지 말고 "✏️ 직접 채우기"로 남긴다. 3. 문서에는 없지만 내용상 자연스럽게 제안하는 문장은 맨 앞에 "(초안)"을 붙여서 구분한다. 4. 프로젝트의 성격(AI 바이브코딩으로 만든 체험형 사이트인지, 소재가 가상 브랜드인지 등)은 문서에 적힌 그대로 쓴다. 가상 브랜드라면 가상이라고 분명히 밝힌다. 5. 03 핵심 가설은 IF를 핵심 인터랙션 하나에 집중하고, THEN은 "끝까지 간다", "다음 단계까지 이동한다"처럼 관찰할 수 있는 행동으로 쓴다. 6. 07 요구사항 & 테스트는 문서의 요구사항 번호와 테스트 케이스 번호를 연결하고, 결과 표와 수정 전/후는 문서에 있는 내용만 쓴다. 7. 08 바이브코딩 구현은 "AI에게 맡긴 것"과 "내가 직접 판단하고 수정한 것"을 분명히 나눠서 쓴다. 8. 10 가설 검증에는 테스트로 확인한 범위(누가, 몇 명이 테스트했는지)라는 한계를 솔직하게 쓴다. 검증된 것처럼 과장하지 않는다. 9. 문장은 짧고 담백하게 쓴다. "혁신적인", "획기적인" 같은 부풀리는 표현은 쓰지 않는다. 10. "인터랙션"으로 표기를 통일한다. ## 출력 형식 - 마크다운, 페이지마다 "## 번호. 제목" - 맨 위에 전체 흐름 표(순서 / 페이지 / 이 프로젝트에서 보여줄 것) - 마지막에 "✏️ 직접 채워야 할 항목 목록"을 한 번에 정리해서 붙인다
